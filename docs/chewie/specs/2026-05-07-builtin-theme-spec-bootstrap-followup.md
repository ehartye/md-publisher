# Follow-up: bootstrap per-theme `spec.json` for built-in themes

**Status:** Deferred from `2026-05-07-mermaid-diagnostics.md` Task 11.
**Owner:** TBD.

## The plan defect

Task 11 of the mermaid-diagnostics plan asked to run `rebuild-themes.py` against the repo's `themes/` directory and commit the refreshed `mermaid-config.json` + `preview.html` for every built-in theme. The migrator dry-run revealed why this isn't possible as-written: **none of the built-in themes have a per-theme `spec.json` file**, so the migrator (correctly) skips all of them with stderr warnings.

The earlier commit `3c8f8fe feat(themes): add default theme palette/fonts to theme-spec.json` updated only the **master** `themes/theme-spec.json` (a multi-theme source-of-truth document); the per-theme `spec.json` files that `theme-advisor:scaffold-theme.py` started persisting later were never backfilled for the bundled themes. So the directory state today is:

```
themes/atlas-light/
  cover.css
  mermaid-config.json   <- generated by an old template; needs refresh
  style.css             <- has the palette as CSS custom properties
  (no spec.json)        <- migrator can't read what it needs
```

vs a properly persisted user theme:

```
~/.md-publisher/themes/chewie-light/
  cover.css
  mermaid-config.json
  preview.html
  spec.json             <- rebuild-themes uses this to regenerate the others
  style.css
```

## What we have to work from

`themes/theme-spec.json` (the master) carries everything we need, but in a different shape from the per-theme `spec.json` that `rebuild-themes.py` consumes. Concretely, for each theme the master holds:

- `themes.<name>.modes.{light, dark}.palette.*` — palette tokens in **camelCase** (`inkSoft`, `accentSoft`, `codeBg`, `codeText`, `tableStripe`)
- `themes.<name>.fonts.{display, body, sansAccent, mono}` — each as a rich object: `{family, weight (or weights[]), opsz?, italic?, _note?}`
- `themes.<name>.mermaid.tagStyling.{light, dark}.{ingress, core, transform, bridge}` — per-mode mermaid styling

The per-theme `spec.json` shape that the migrator already understands is flatter:

- `palette.*` in **snake_case** (`ink_soft`, `accent_alt`, `code_bg`, `code_text`)
- `fonts.{display, body, sans, mono}` as **CSS font-stack strings** (e.g. `"Newsreader, Georgia, serif"`)
- `mermaid.tagStyling.{ingress, core, transform, bridge}` (no per-mode nesting at this level — the spec file IS already mode-specific)

## Schema mapping questions to design

These are the open design choices the bootstrap script (or hand-conversion) has to settle:

1. **Font shape collapse.** Master `fonts.<role>.{family, weight, opsz, italic}` → spec `fonts.<role> = "Family, Fallback1, Fallback2"`. The richer typography metadata (variable-font axis values, italic flags) does NOT round-trip — it lives only in `style.css` as CSS custom properties. Decision: drop it on the floor in `spec.json` (acceptable — it's not used by the mermaid-config or preview templates) OR extend `spec.json`'s schema to carry it (broader change, would require updating `_spec_to_substitution_dict` in rebuild-themes.py and likely scaffold-theme.py too).
2. **Sans-key naming.** Master uses `sansAccent`; spec uses `sans`. Mechanical rename, but worth confirming whether any future `style.css` template wants to distinguish "structural sans" from "accent sans."
3. **Fallback stacks.** Master only names one family per role; per-theme `spec.json` historically embeds a 2-3 family fallback chain (`"Newsreader, Georgia, serif"`). Where do the fallbacks come from? Either: re-derive from the existing `themes/<theme-mode>/style.css` (parse the CSS custom properties), or hard-code per-role generic fallbacks (`serif` / `sans-serif` / `monospace`) in the bootstrap script.
4. **Per-mode emission.** Master groups `modes.{light, dark}` under one theme entry. The bootstrap must emit TWO files per theme — `themes/<theme>-light/spec.json` and `themes/<theme>-dark/spec.json` — each with its own `mode` field, palette, and mermaid tagStyling slice.
5. **Default theme.** `themes/default/` exists as a single directory (no `-light`/`-dark` suffix). Decision: emit `spec.json` with `mode: "light"` (current behavior of `default`) and skip dark, OR add a `default-dark/` and split.
6. **`tagline` and `displayName`.** The master has `displayName` and `tagline` for each theme; both pass through directly. No transformation needed — just propagate.

## Why the migrator doesn't need to change

`rebuild-themes.py` already handles the missing-spec case gracefully: it logs a `[rebuild-themes] skip <name>: missing spec.json` warning and continues. Once each built-in theme directory has a `spec.json`, re-running `/md-publisher:rebuild-themes --apply` will refresh `mermaid-config.json` and `preview.html` exactly as designed for user themes.
